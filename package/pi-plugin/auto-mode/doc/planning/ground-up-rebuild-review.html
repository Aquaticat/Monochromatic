Open decision / Q1

When is a four-choice answer decisive?

The old formula used an explicit unknown choice. The new response has four different labels; ask is not automatically unknown, and confidence is separate metadata.

Same answer: approve 0.46 · deny 0.04 · ask 0.29 · not-applicable 0.21.

A. Require a unique leading probability of at least 0.6

Benefit: The split example stays unresolved and can be refined.

Cost: More follow-ups or human reviews; 0.6 still needs calibration.

B. Accept any unique leading probability

Benefit: The example immediately admits approve; fewer unresolved distributions.

Cost: A plurality is treated as sufficient even when most probability lies elsewhere.

Ranking: A > B because the split example does not establish a decisive answer. Exact ties and invalid or missing responses stay unresolved in either option.

Open decision / Q2

What does an admitted ask mean?

This concerns an answer that already passes the numeric admission rule. A weak or missing answer can remain unresolved without adding a fifth choice.

A rule requires the human to select the account to charge. No account choice exists in the conversation.

A. An established ask routes to the human immediately

Benefit: Avoids model questions that cannot supply a human preference.

Cost: A mistaken but decisive ask reaches the human without further model refinement.

B. Every ask uses remaining follow-up batches first

Benefit: Gives an ambiguous ask more chances to be resolved.

Cost: Can repeat review when the missing input is inherently a human decision.

Ranking: A > B because a confident need for human input is itself a resolved disposition. In both options, unresolved answers may use the remaining batches.

Open decision / Q4

Keep the latest human request outside the history cap?

The pending group is always complete. This choice concerns the separate history input: five to ten assistant blocks or tool-call sets since the latest genuine human message.

Twelve units after “review only”, the latest ten units discuss possible implementation edits.

A. Retain the latest human request separately

Benefit: Preserves the review-only authorization boundary alongside the capped recent history.

Cost: Adds that request beyond the historical window.

B. Keep only the capped history

Benefit: Maintains a literal cap on historical input.

Cost: Can lose review-only scope and require asking when authorization cannot be established.

Ranking: A > B because the original request remains authoritative when it becomes less recent. Feedback and compaction messages do not reset the human anchor.

Open decision / Q6

Adopt upfront preparation for guarded sequential groups?

Pi currently prepares A, executes A, then prepares B. Reviewing a complete prepared group moves B’s preparation before A executes.

A writes a file. B’s preparation hook reads the new file to determine B’s arguments.

Current Pi

Prepare A → Execute A → Prepare B → Execute B

B’s hook sees A’s output.

Complete prepared-group contract

Prepare A + B → Review group → Execute A → Execute B

B’s hook runs before A. Result-dependent B needs a later group.

A. Prepare the whole group once, then execute frozen arguments in order

Benefit: Provides a usable complete-group contract. Result-dependent B must be submitted as a later group.

Cost: Changes hook timing; incompatible result-dependent groups need an actionable rejection.

B. Leave incompatible groups blocked pending compatible host support

Benefit: Makes the compatibility limit explicit without claiming unchanged behavior.

Cost: Those grouped operations remain unavailable while integration support is unresolved.

Ranking: A > B if upfront preparation is auto-mode’s documented contract, because it supplies an executable group model. Neither choice executes A before initial group review.
