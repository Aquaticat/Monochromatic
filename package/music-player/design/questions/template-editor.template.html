Design study. A built editor for the supporting-line template, and one question about it.

Editing the track row's supporting line

Purpose: look at a built editor for the template that produces a track row's supporting line (D81). The language and the editor follow KWGT with the omissions you chose (D89) and the picks you left to the agent (D90). Nothing on this page is decided by being shown.

Every state is authored debug input. Typing is not connected: each view shows fixed template text, and the preview, error lines and help it draws are checked against a reference that computes what the grammar yields. The app has a duration only for the playing track today and draws no supporting line yet, so this previews a line the app cannot fill for every row.

The buttons emit debug events only. No template is stored and no row of the player changes. No production implementation is authorized.

Inspect the same native conditions

Thumbnails fit the review column. Open any image to inspect it at 100% logical dp or native pixels. These are sanitized app-area crops, not device mockups. Status strips were removed for privacy; bottom navigation remains. Logical dp uses the measured 390dpi density, not your monitor's physical size.

The editor's states

These views use the baseline layout: the preview at the top of one scrolling page. Three states hold focus in the template field with the system keyboard open. Under each image, the page says what of that state is not in view.

What this study assumes

None of this is asked as a question, because each point was either decided or left to the agent (D89, D90). If one should change, say so in the last field of this page.

  • One template is studied: the supporting line of a track row. Titles and other rows are not templated here.
  • Spelling follows KWGT: formulas between dollar signs, mi(field) for a field of the track, tf(seconds, format) for a duration, tc(mode, text) for case and cutting, if(condition, then, else), and + to join text.
  • Fields: title, file, ext, folder, path, len and peak. There is no artist or album field, because the app reads no tags.
  • The default template gives the duration and, once a file is analysed, its true peak: $tf(mi(len), m:ss)$$if(mi(peak) != "", " · " + mi(peak) + " dBTP")$.
  • The preview shows two files of the open library, one of them not analysed yet, and sample values when no library is open.
  • An edit applies as typed while the template is valid. While it has a mistake, rows keep the last valid template. There is no Save step; Reset to default is drawn only when the template differs from the default.
  • A mistake is named under the field in place of the typing help. A formula left open is a mistake.
Question: what stays in view while typing

Why this is asked: at 100% text everything around the field fits above the keyboard on both panels. At 200% text it does not, and something has to give. The baseline lets the preview scroll away, which hides the result of each keystroke. Two alternatives keep the preview fixed under the header. In all three, the page scrolls while the field has focus so that the lines under the field clear the keyboard, as far as they fit.

The lines marked Measured under each option are read from the captures. They count the preview, the field and the lines under it. The field list sits under the field in every option and is mostly out of view whenever the keyboard is open; that is a separate concern, named at the end of this page.

Preview at the top of the page (the baseline)

The two preview rows are the first thing on one scrolling page.

  • For: the simplest page, with nothing fixed but the header, so the field and its lines get all the height when they need it.
  • Against: at 200% text the preview is not in view while typing, so the result of a keystroke is seen only after scrolling back.

    Both preview rows fixed under the header

    The two preview rows never scroll; the note, the field and the field list scroll beneath them. KWGT also keeps its preview fixed above the formula field.

    • For: the result of every keystroke stays in view at every size, drawn as the track row it will become, title and line.
    • Against: it takes the most height. At 200% text less of the help under the field fits, and at rest the scrolling part of the page is shorter.

      Only the two result lines fixed under the header

      Only what the template yields for the two files stays fixed, one line each, without the rows' titles. KWGT's own preview is one such line.

      • For: the result stays in view for less height than two whole rows, so more of the field's help fits at 200% text.
      • Against: the lines no longer look like track rows, and only their order says which file each belongs to; the note that explains the second line scrolls away.

        __RANKING__

        Read what was and was not checked

        The host is a debug activity, not the player. The merged debug manifest disables the production launcher, playback and sweep services. Each view was captured with a fresh hierarchy, exactly one creation of the host since its launch, and the keyboard open only for the three states that hold focus.

        Whether a text is in view is read from its rectangle in the hierarchy, the page's scrolling window and the keyboard's own frame; hierarchy rectangles are not ink bounds. A text whose rectangle touches an edge of the window is reported as at the edge, because the hierarchy cannot tell cut from flush. Where the page rests with the keyboard open is the study's own scroll rule, applied once per launch. TalkBack, focus order, speech and contrast were not exercised. Real typing, caret movement by touch, scrolling by hand and inserting a field were not exercised.

        Not built yet: with the keyboard open most of the field list is out of view, so inserting a field means scrolling away from the field. What to do about that depends on the answer to the question, and comes after it.

        The published crops keep exact RGB, opacity, dimensions and only essential PNG chunks. No digest of an image is recorded, and nothing is compared with a digest (D88).
