### Decided: queue tool calls, free only the read loop

`serve()` awaits each dispatch inline in the stdin read loop,
so a `run_in_vm` that takes 15 to 30 minutes blocks the loop:
the server cannot even read `notifications/cancelled` while it runs.
The spec says a cancelled request's associated processing **SHOULD** cease.

The user chose the narrowest shape that fixes the actual complaint.
Only the read loop becomes concurrent.
Tool execution stays serialized behind a queue,
 so exactly one handler runs at a time,
 exactly as today.
`ToolHandler` keeps its current signature and no `AbortSignal` is introduced.

The payoff beyond merely reading cancellations:
 a cancelled request that is still queued and has not started yet is dropped before it ever runs.
That is strictly better than aborting one midway,
 because nothing has happened yet to leave half-done.

What this deliberately does not do,
 and why:

-   For a request already executing,
     it does not satisfy the spec's SHOULD that processing cease.
    That request runs to completion.
    Aborting `create_vm` or `update_templates` midway can strand a half-created VM
    or a half-built image,
     which is worse than letting it finish.
-   It gains no parallelism for genuinely independent calls.
    A `list_vms` issued during a long `create_vm` waits behind it.
    That cost was accepted deliberately in exchange for introducing no new interleaving.

Writes must still go through one queue,
 or frames interleave on stdout.

#### Narrowed from an earlier, broader shape

An earlier round recorded this as "concurrent dispatch, no `AbortSignal`",
 meaning handlers would run concurrently and only outbound writes would be serialized.
That shape carried an open worry:
 concurrent handlers let two VM mutations interleave where the transport had been
serializing them by accident rather than by design,
 which could open races in the mvm backend that did not exist before.

Serializing execution removes that worry rather than answering it.
There is no mvm race audit to perform before landing,
 because no two handlers ever run at once.
The transport's accidental serialization becomes deliberate.

### Decided: validate with valibot

The user's answer:
 "We already have valibot as a workspace dep."
Confirmed present,
 `pnpm-workspace.yaml:147` pins `valibot: '>=1.4.2'`,
resolved to `valibot@1.4.2`,
 already consumed by five workspace packages including
`package/git-policy/forbidden-strings` and `package/ssg/aquati.cat`.

This rules out the hand-rolled subset,
 a new external dependency,
 and leaving it to handlers.

Open design point to settle before building,
 since valibot schemas are not JSON Schema and
`inputSchema` must still go out on the wire as JSON Schema 2020-12:

-   Preferred shape:
     a tool declares one valibot schema,
     the advertised `inputSchema` is derived
    from it,
     so the contract clients see and the contract enforced cannot drift.
    Deriving needs `@valibot/to-json-schema`,
     which is **not** currently installed
    (only `valibot@1.4.2` is present),
     so adding it is part of this work.
-   Fallback if that package is unsuitable:
     keep both,
     and add a test asserting the pair agree
    on a fixed set of accepted and rejected argument objects,
     so drift fails the suite.
-   `destroy_vm` is the hard case:
     its rule is "exactly one of `name` or `all`",
     expressed today
    as `oneOf`/`not`/`const` in JSON Schema and as a handler guard.
    Whatever lands must keep the handler guard,
     because the guard is what actually prevents
    destroying every VM,
     and must not weaken it to a schema that only a well-behaved client honors.

## How to verify anything here

Both packages build,
 lint,
 type-check,
 and test through mise:

```sh
mise run //package/mcp/stdio:lint
mise run //package/mcp/stdio:buildAndTest
mise run //package/mcp/mvm:lint
mise run //package/mcp/mvm:buildAndTest
```

`buildAndTest` is required rather than `test:unit` alone:
both suites import the built artifact,
 so a source-only run tests stale output.

End-user verification goes through the client,
 not the test suite:

```sh
mise run //package/mcp/mvm:build
claude mcp get mvm
```

To see the actual wire exchange,
 register a tap that pipes stdio through to the real bin
while appending both directions to a log,
 then health-check the tap.
That is how the modern-path negotiation was confirmed;
the recipe is in the planning doc's verification section.

## Gotchas worth knowing before editing

-   **Read the full lint output,
     never a grep of its summary lines.**
    The rules in this repo carry ranked remediation instructions in the message body.
    Grepping cost a wrong fix once already:
     `no-nullish-union` names an empty object outright
    as a banned stand-in for absent,
     which a summary-line grep hides.
-   **Tests must import built output,
     not package source.**
    `require-eventual-artifact` enforces it.
    A behavior only reachable through a source symbol gets tested over stdio through the bin instead.
-   **Never let a `destroy_vm` test reach a real backend.**
    Every such case pins `backend` to a kind nothing resolves,
    so even an accepted call cannot destroy anything.
-   **`~/.claude.json` is rewritten by concurrent sessions.**
    Change MCP registrations with `claude mcp add`/`remove`,
     never by hand-editing the file.
-   **The client caches server era per process.**
    After changing protocol behavior,
     rebuild before re-running `claude mcp get`,
    or the health check exercises the previous binary.
