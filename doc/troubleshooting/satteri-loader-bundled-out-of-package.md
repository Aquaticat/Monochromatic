# Sätteri 0.9.5 bundled through markdown-lint makes translation-repair miss its native binding

## Symptom

After `@monochromatic-dev/module-translation-repair` began importing
`@monochromatic-dev/cli-markdown-lint/ts`,
every import of the built translation-repair package threw before pipeline code ran:

```text
Error: Cannot find native binding. npm has a bug related to optional dependencies
(https://github.com/npm/cli/issues/4828). Please try `npm i` again after removing
both package-lock.json and node_modules directory.

[cause]: Error: Cannot find module '@bruits/satteri-linux-x64-gnu'
code: 'MODULE_NOT_FOUND'
```

The emitted tool is Sätteri's generated NAPI loader,
not npm,
pnpm,
or Rolldown.
The npm explanation is incorrect for this incident:
the matching binding is installed,
but the copied loader resolves from the generated translation-repair chunk instead of Sätteri's package directory.

A related false-success signal occurs when Sätteri's own binding link is absent:
`mise run //package/cli/markdown-lint:build` still succeeds because the bundle keeps Sätteri external,
then the built CLI throws the same error when loaded.

## Root cause

### Translation-repair reaches markdown-lint's parser

`package/module/translation-repair/src/semantic-wrap.ts:1-5` imports the fixer and rule registry from the
CLI package's source subpath:

```ts
import {
  fixSource,
  type Rule,
  rulesById,
} from '@monochromatic-dev/cli-markdown-lint/ts';
```

The CLI package root re-exports the fixer,
rule runner,
and parser together at `package/cli/markdown-lint/src/index.ts:1-6`:

```ts
export {
  applyFixes,
  fixSource,
} from './fix.ts';
export { runRules, } from './lint.ts';
export { parse, } from './parse.ts';
```

The static closure reaches Sätteri step by step:

- `package/cli/markdown-lint/src/fix.ts:1` imports `runRules`.
- `package/cli/markdown-lint/src/lint.ts:1` imports `parse`.
- `package/cli/markdown-lint/src/lint.ts:43-56` parses once and passes that tree to each rule.
- `package/cli/markdown-lint/src/parse.ts:1-5` imports `markdownToMdast` and `mdxToMdast` from `satteri`.

```ts
// package/cli/markdown-lint/src/lint.ts:43-56
export function runRules({
  rules,
  source,
  mdx,
}: RunRulesParams,): readonly Diagnostic[] {
  const tree = parse({
    source,
    mdx,
  },);
  return rules.flatMap(function checkRule(rule: Rule,): readonly Diagnostic[] {
```

```ts
// package/cli/markdown-lint/src/parse.ts:1-5
import type { Root, } from 'mdast';
import {
  markdownToMdast,
  mdxToMdast,
} from 'satteri';
```

Moving only the rule files would therefore leave the native dependency reachable through the fixpoint loop.
A parser-free design must move or parameterize the loop as well.

### The shared Node build inlines undeclared transitives

`package/config/rolldown/src/index.node.ts:26-30` forces every workspace package into Node bundles:

```ts
export const NODE_ALWAYS_BUNDLE: readonly string[] = [
  '@monochromatic-dev/**',
  'find-up',
  'nano-spawn',
];
```

`package/config/rolldown/src/package-externals.ts:219-230` derives externals only from the consuming package's
declared dependencies and peers,
then removes names matched by an always-bundle pattern:

```ts
const externalNames = Object.keys({
  ...manifest.dependencies,
  ...manifest.peerDependencies,
})
  .filter(function isExternalName(name: string): boolean {
  return !alwaysBundle.some(function matchesName(pattern: BundlePattern): boolean {
    return matchesBundlePattern({
      name,
      pattern
    });
  });
});
```

`package/config/rolldown/src/index.node.ts:83-90` installs that result in every shared Node config:

```ts
const baseOptions: RolldownOptions = {
  platform: 'node',
  external: await nodeExternal({ alwaysBundle: NODE_ALWAYS_BUNDLE, },),
  transform: { target: [...target,], },
  plugins: [
    dts({ generator: 'oxc', },),
    shebangExecutablePlugin(),
  ],
};
```

Before workaround commit `34f4320a8`,
translation-repair declared markdown-lint but did not declare Sätteri.
Rolldown therefore inlined markdown-lint because it is a workspace package,
then continued into the undeclared Sätteri dependency and copied its generated loader into a
`dist/final/node/repair-translation-*.mjs` chunk.

### Sätteri resolves relative to the loader file

The cloned Sätteri `0.9.5` source is `bruits/satteri@92d01ec4` (`satteri-v0.9.5`).
Its generated loader creates a CommonJS resolver from its own module URL at
`packages/satteri/index.js:1-8`:

```js
// prettier-ignore
/* eslint-disable */
// @ts-nocheck
/* auto-generated by NAPI-RS */

import { createRequire } from 'node:module'
const require = createRequire(import.meta.url)
const __dirname = new URL('.', import.meta.url).pathname
```

On Linux x64 glibc,
`packages/satteri/index.js:285-299` first tries a binary beside that loader,
then its platform package:

```js
try {
  return require('./satteri_napi.linux-x64-gnu.node')
} catch (e) {
  loadErrors.push(e)
}
try {
  const binding = require('@bruits/satteri-linux-x64-gnu')
  const bindingPackageVersion = require('@bruits/satteri-linux-x64-gnu/package.json').version
  if (bindingPackageVersion !== '0.8.1' && process.env.NAPI_RS_ENFORCE_VERSION_CHECK && process.env.NAPI_RS_ENFORCE_VERSION_CHECK !== '0') {
    throw new Error(`Native binding package version mismatch, expected 0.8.1 but got ${bindingPackageVersion}. You can reinstall dependencies to fix this issue.`)
  }
  return binding
} catch (e) {
  loadErrors.push(e)
}
```

`packages/satteri/index.js:530-578` performs that lookup during module evaluation and emits the observed error after
native,
WASI,
and WebContainer attempts fail:

```js
nativeBinding = requireNative()

// WASI and WebContainer fallbacks omitted

if (!nativeBinding) {
  if (loadErrors.length > 0) {
    throw new Error(
      `Cannot find native binding. ` +
        `npm has a bug related to optional dependencies (https://github.com/npm/cli/issues/4828). ` +
        'Please try `npm i` again after removing both package-lock.json and node_modules directory.',
```

Inside Sätteri's installed directory,
`createRequire(import.meta.url)` can see pnpm's nested `@bruits` links.
Inside translation-repair's generated chunk,
the same call starts from `dist/final/node`.
Strict pnpm isolation does not expose Sätteri's nested binding package there,
so both native attempts fail even though `pnpm-lock.yaml:4306-4310` and
`pnpm-lock.yaml:9938-9953` record the package and dependency relationship.

The earlier reading that this was an npm optional-dependency installation failure was wrong.
The installed binding file and markdown-lint's successful direct parse disprove it;
the resolver base changes only after Rolldown copies the loader.

### Patterns that work cleanly

- **Sätteri loaded from its own package directory**:
  the binding file exists under
  `node_modules/.pnpm/@bruits+satteri-linux-x64-gnu@0.9.5/`,
  and markdown-lint's built CLI parses a clean Markdown fixture to `[]`.
- **Current translation-repair workaround**:
  `package/module/translation-repair/package.json:29` declares `satteri`.
  Its build retains one `from"satteri"` import,
  copies no loader error string,
  and the built package imports successfully.
- **Parser-free semantic-wrap probe**:
  the existing semantic rule plus translation-repair's existing remark/GFM parser produced output identical to the
  Sätteri-backed fixer on thirteen measured fixture shapes.
  With the native binding link removed,
  direct Sätteri import failed while the parser-free probe still fixed text successfully.

### Patterns that fail

- **Workspace source inlined without declaring Sätteri**:
  Rolldown succeeds,
  one generated chunk contains the loader error,
  and built-package import throws `MODULE_NOT_FOUND` for the platform binding.
- **Sätteri externalized generically without a consumer dependency**:
  the copied loader disappears,
  but built-package import throws `ERR_MODULE_NOT_FOUND` for bare package `satteri`.
- **Markdown-lint build with its own native link absent**:
  Rolldown succeeds because Sätteri stays external,
  then loading the built CLI throws `Cannot find native binding`.

## Verified workarounds

### Declare Sätteri in every bundling consumer

Workaround commit `34f4320a8` adds the direct dependency:

```diff
diff --git a/package/module/translation-repair/package.json b/package/module/translation-repair/package.json
@@
     "remark-gfm": "catalog:",
+    "satteri": "catalog:",
     "remark-mdx": "catalog:",
```

Declared dependencies stay external,
so Rolldown emits `import ... from "satteri"` and Node evaluates the loader from Sätteri's own package directory.
Verify the built boundary:

```console
$ mise run //package/module/translation-repair:build
$ rg --count-matches 'from"satteri"' package/module/translation-repair/dist/final/node/*.mjs
$ rg --files-with-matches 'Cannot find native binding' package/module/translation-repair/dist/final/node
$ node --input-type=module --eval \
    "await import('./package/module/translation-repair/dist/final/node/index.mjs')"
```

Tradeoffs:
translation-repair declares and installs a native package it never imports in source;
every future workspace consumer must rediscover the transitive requirement;
and platform-binding availability remains part of that consumer's runtime contract.
This is safe as a short-term workaround,
not a durable module seam.

### Externalize the whole markdown-lint package

A prototype added `@monochromatic-dev/cli-markdown-lint` to
`NODE_ALWAYS_EXTERNAL` in `package/config/rolldown/src/index.node.ts`.
With no direct Sätteri declaration,
translation-repair retained one markdown-lint import,
copied no loader,
and imported successfully inside the workspace.

Tradeoffs:
it contradicts the self-contained workspace-bundle policy,
keeps the unnecessary native dependency,
special-cases one package rather than expressing a reusable design,
and leaves a public package's artifact importing the currently private markdown-lint package.
It is not suitable for publishing translation-repair.

## Recommended migration

Create parser-free package `package/module/markdown-lint`
(`@monochromatic-dev/module-markdown-lint`) with this small seam:

```ts
import type { Root, } from 'mdast';

export type ParseMarkdown = (params: {
  readonly source: string;
  readonly mdx: boolean;
}) => Root;

export function runRules(params: {
  readonly parse: ParseMarkdown;
  readonly rules: readonly Rule[];
  readonly source: string;
  readonly mdx: boolean;
}): readonly Diagnostic[];

export function fixSource(params: {
  readonly parse: ParseMarkdown;
  readonly rules: readonly Rule[];
  readonly source: string;
  readonly mdx: boolean;
}): FixSourceResult;
```

The parser callback must return a root for the exact source with offsets expressed as JavaScript UTF-16 string indexes.
The package owns rule dispatch,
fix ordering,
overlap handling,
reparsing after every changed pass,
and final diagnostics.
It exports rules,
`rulesById`,
and rule/fix types,
but imports no parser.

Two adapters make this a real seam:

- markdown-lint keeps its Sätteri adapter,
  including code-point to UTF-16 offset correction,
  and preserves current convenience wrappers for CLI callers;
- translation-repair injects its existing `parseMarkdownBody` remark/GFM parser and drops both
  `@monochromatic-dev/cli-markdown-lint` and `satteri` dependencies.

The thirteen-fixture parity probe validates the seam,
not the migration.
Completion still requires the complete semantic-wrap suite,
corpus parity,
bundle marker checks,
a built translation-repair call with the native link hidden,
and package installation in a disposable non-workspace consumer.

Add a complementary markdown-lint build smoke that imports the built library and calls `parse` on a clean source.
Calling the parser is stronger than checking `--help` because it remains effective
if Sätteri ever defers native loading.
The smoke detects a broken native artifact;
it does not replace the parser-free split.

## What does not work

### Reinstalling npm or pnpm dependencies

The binding is already installed and works from Sätteri's own location.
Reinstalling recreates the same correct nested pnpm layout;
it does not move the inlined loader back under Sätteri.

### Adding `packageExtensions` to Sätteri

`packageExtensions` can repair a package that imports an undeclared dependency from its own directory.
This loader has been copied out of that directory.
Adding links under Sätteri does not make them visible from translation-repair's generated chunk.

### Always externalizing detected NAPI packages

A prototype always externalized bare `satteri` and removed the stale direct consumer link.
The build emitted an external import,
then runtime failed with:

```text
Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'satteri' imported from
.../package/module/translation-repair/dist/final/node/repair-translation-*.mjs
```

Detection alone only changes the error.
The output still needs an honest direct runtime dependency,
which is the manual workaround the proposal intended to eliminate.

### Trusting a green Rolldown build

Rolldown resolves and emits module structure;
it does not evaluate the external Sätteri package or the generated loader.
The fresh-worktree harness produced a successful build and failing import repeatedly.
A built-artifact smoke is required for readiness evidence.

### Moving only rules

`fixSource` imports `runRules`,
which imports `parse`,
which imports Sätteri.
A package containing rules but re-exporting the existing fixer still carries the native dependency.
Move the fixpoint implementation behind the parser callback as part of the same migration.

## Upstream filing decision

No `.out-of-scope/` entry matches Sätteri,
NAPI loader bundling,
or Rolldown.

Searches covered every open and closed Sätteri issue and pull request for
`native binding`,
`cannot find`,
`bundle`,
and `napi`.
Issue [bruits/satteri#163](https://github.com/bruits/satteri/issues/163) and merged pull request
[bruits/satteri#136](https://github.com/bruits/satteri/pull/136)
concern missing WASI runtime dependencies under browser bundling.
They do not describe a native loader copied out of its package.
Issue [bruits/satteri#209](https://github.com/bruits/satteri/issues/209) concerns the generated loader's stale
version check and is also not a duplicate.

1. **Is it really upstream's fault?**
   No.
   Sätteri's loader works from the package layout it publishes.
   Monochromatic's shared Rolldown policy copies that loader while inlining undeclared transitive dependencies.
2. **Can upstream fix it?**
   Partly.
   Upstream could document that the native loader must remain at its package seam or design a relocation mechanism,
   but it cannot make Monochromatic's generated package manifest honestly declare a runtime dependency.
3. **Are they supporting this use case?**
   No evidence says so.
   `packages/satteri/README.md` documents normal package imports,
   and `CONTRIBUTING.md` describes the NAPI binding,
   but neither promises that consumers may copy the generated loader into an unrelated server bundle.
4. **Would the repository welcome our contribution?**
   Contributions are welcome under `CONTRIBUTING.md`,
   which requests duplicate checks,
   detailed reports,
   tests,
   and focused changes.
   The issue templates are open,
   and no policy banning AI-assisted reports was found.
   This constraint does not override the fault and support failures.
5. **Will they likely fix it?**
   Unknown,
   with no maintainer response on this exact shape.
   Recent commits still change `packages/satteri/index.js`,
   and maintainers have accepted packaging fixes such as pull request 136,
   but there is no signal that arbitrary relocation is a supported goal.
6. **Have we prototyped a minimal fix compatible with their architecture?**
   No upstream fix was prototyped because constraints 1 and 3 fail.
   Consumer-side prototypes instead proved the direct declaration,
   whole-package externalization,
   generic-externalization failure,
   and parser-free seam.

The filing constraints do not pass,
so nothing should be filed upstream.
The project-local report remains issue
[Aquaticat/Monochromatic#447](https://github.com/Aquaticat/Monochromatic/issues/447).

### Description

A Node consumer using Sätteri 0.9.5 copied `packages/satteri/index.js` into another package's generated bundle.
The loader uses `createRequire(import.meta.url)` and therefore resolved

Bundle Sätteri's generated loader into an unrelated package directory without declaring Sätteri as a runtime dependency,

- `packages/satteri/index.js:6-8` creates `require` from `import.meta.url`.
- `packages/satteri/index.js:287-299` loads the Linux x64 GNU sidecar.
- `packages/satteri/index.js:530-578` evaluates the loader and emits the generic missing-binding error.

No loader change is justified by the current evidence.
