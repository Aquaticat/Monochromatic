Every way to give pi a provider API key

A plain-language map of all the doors, what each one costs you, and which one to walk through. Written so a monkey (a very handsome monkey) can pick correctly the first time.

pi 0.87.1 docs ✓ claims marked verified were run on this machine one mechanism excluded by request (see below)

What this doc deliberately leaves out

You asked me to omit the status quo of your current setup: the plaintext literal apiKey sitting in models.json. So that arrangement gets no card, no recommendation, and no comparison row in the detailed sections.

Everything else pi supports is here. The one-line reason the excluded arrangement is not recommended is the same reason this whole doc exists: keys printed or read by agents end up in transcripts, and the file that holds it is world-readable by default.

The quick answer

If you read nothing else, read this ladder. It goes from "most hidden from casual probes" to "most exposed".

  1. Secret manager behind an auth.json command. The key lives in an OS keyring or an encrypted store. Pi asks for it only when it needs it. Nothing on disk holds the secret itself.
  2. Literal key in auth.json. One private file (permissions 600), one place to rotate, resolved inside pi without any process ever printing it.
  3. Stored sign-in via /login. Same file as above, but pi writes it for you after an OAuth or API-key flow. Fine when the provider supports it.
  4. Runtime --api-key flag. Great for one-off runs, terrible for secrecy: the key sits in the command line where ps can see it.
  5. Environment variable. Works everywhere including CI. Worst casual-exposure surface of the set: every env dump, every child process, every crash log can carry it.

Rule of thumb: the question is never "can a determined attacker get the key" (if they run as you, they can). The question is "how many innocent-looking commands accidentally print it". Each rung above answers that question better than the one below it.

How pi picks a key when several exist

Pi resolves credentials in a fixed order. Whichever source wins higher is the one that gets sent. The order comes from pi's own docs (docs/models.md), and I confirmed the first three rungs by pointing pi at a local echo server and reading the Authorization header of real requests.

  1. Runtime --api-key flag ✓ verified
    Observed Bearer from-flag even with both other sources configured. Also works alone, with nothing stored anywhere.
  2. Stored credential in auth.json ✓ verified
    Observed Bearer from-authjson while a different key sat in models.json.
  3. apiKey (or custom headers) in models.json ✓ verified
    Observed Bearer from-modelsjson when it was the only source.
  4. Provider environment variables or ambient cloud credentials docs
    Lowest priority. Note the built-in env-var names (like ANTHROPIC_API_KEY) apply to pi's built-in providers. A custom provider invented in models.json does not get a NAME_API_KEY fallback: I tried TESTPROV_API_KEY and pi sent no request at all ✓ verified.

Side effect worth knowing: if a model "mysteriously" does not appear in /model, pi may simply have no resolvable credential for its provider. Pi's own troubleshooting note says custom models stay hidden until credentials resolve.

Who can see your key, in plain terms

A key is not stolen by magic. It leaks when some ordinary action copies it somewhere durable. These are the ordinary actions that matter.

💬 Tool output becomes transcript

Anything an agent prints or reads lands in the session .jsonl file. Pi's own security doc warns: "Review sessions before exporting or sharing them. They can contain prompts, tool arguments, command output, file contents, and credentials exposed during the conversation."

🌍 Environment dumps

env, printenv, and a bare echo $PI_* style probe print every variable in the process. Agents run these constantly while investigating. Your argument, and it is correct.

👁 Process listings

On Linux the same user can read another process's environment and command line (ps eww, /proc/<pid>/environ, ps aux). Command-line keys and env keys are both visible here. (Platform fact.)

👶 Child processes inherit

Every tool command, build, and test runs as a child of the agent process. Environment variables ride along into all of them, including third-party scripts that log their environment on error.

📁 File permissions

A secret in a 644 file is readable by any account on the machine. A secret in a 600 file is readable only by you (and by anything running as you, which includes the agent).

🧾 Logs and crash reports

Debug builds, HTTP debug logs, error trackers, and core dumps happily serialize environment and headers. Rare events, big consequences.

The BOOM scenario

You store the key in an environment variable. Later, an agent (any agent, in any session) runs env | grep PI_ or similar to answer an innocent question about its configuration. The full key is printed. The print lands in the session transcript. The transcript is a plain file that gets shared, backed up, or summarized into another model's context. The key is now public-ish forever, and only rotation fixes that.

The safest habit: arrange things so that no ordinary command has a reason to print the key, and so that if it is printed, it is a fake or masked value.

The catalog: every mechanism

Each card says what the mechanism is, how to set it up, where the key physically rests, and what happens when it fails. Evidence badges: ✓ verified means I ran it on this machine, docs means it comes from pi's published docs, platform means general OS behavior.

Mechanism 1: sign in with /login (OAuth or guided API-key flow)

Run /login inside pi and pick the provider. Pi walks you through a browser sign-in (OAuth) or an API-key paste, then saves the result itself.

Where the key rests
<agent-dir>/auth.json (default ~/.pi/agent/auth.json), which is a private 600 file.
Setup
/login, pick provider, follow prompts. Remove with /logout.
Headless machines
docs When an OAuth callback cannot reach your machine, pi lets you paste the final redirect URL or authorization code back in.
Watch out
docs /logout only removes the stored credential. It does not unset environment variables, remove models.json authentication, or revoke anything at the provider.
Best for
Any provider pi knows natively. The boring, correct default.
Mechanism 2: literal API key stored in auth.json

Put the key in pi's credential file by hand (or through your own tooling). This is the same file /login writes, just without the guided flow. Useful for custom endpoints where no sign-in flow exists. 

# ~/.pi/agent/auth.json
{
  "my-provider": {
    "type": "api_key",
    "key": "sk-..."
  }
}
Where the key rests
Inside auth.json, permissions 600. One file, one rotation point.
Precedence
✓ verified Beats any apiKey in models.json (observed on real requests).
Watch out
Still plaintext on disk. An agent that inspects auth config will see it (mask values when probing, like the python3 one-liner in the evidence section).
Best for
Custom OpenAI-compatible endpoints where you want simple, private, one-place rotation.
Mechanism 3: auth.json command (!...), keyring or encrypted store

Instead of the key itself, store a command that prints the key. Pi runs it only when the key is first needed. The secret never sits in pi's config at all; it lives wherever your secret manager keeps it. 

# ~/.pi/agent/auth.json
{
  "my-provider": {
    "type": "api_key",
    "key": "!secret-tool lookup service my-llm user me"
  }
}

The macOS example from pi's docs is !security find-generic-password -ws 'anthropic'. Any command works: OS keyring, a password manager CLI, or a decrypt-and-print script.

Where the key rests
Only in the secret manager. Not in the environment, not in pi's files.
Timing and caching
docs Pi runs the command when the key is first needed and caches its standard output for the lifetime of the pi process.
Failure mode (important)
docs "Empty output, a timeout, or a nonzero exit leaves the key unresolved until Pi restarts." A locked keyring therefore breaks the session until restart, with no automatic retry.
Shell behavior
✓ verified The command runs through a shell: $HOME expanded in my probe, so pipelines, quoting, and VAR=value cmd prefixes work.
Best for
The strongest practical option on a personal machine with a keyring or encrypted store. See the sops recipe below for a concrete version.
Mechanism 4: models.json apiKey with variable interpolation

In a custom endpoint definition, the apiKey field accepts $NAME or ${NAME}. Pi substitutes the value from the process environment at request time. 

# ~/.pi/agent/models.json
{
  "providers": {
    "my-provider": {
      "baseUrl": "https://api.example.com/v1",
      "api": "openai-completions",
      "apiKey": "${MY_PROVIDER_KEY}",
      "models": [{ "id": "some-model" }]
    }
  }
}
Where the key rests
In the environment of the process that started pi. The config file holds only the variable name.
Exposure
env-exposed All the environment problems above apply. This option is honest about it and useful where that risk is accepted (CI, containers).
Watch out
docs Environment variables must be present in the process that starts pi. A key exported in your interactive shell will not appear if pi is launched from a desktop entry, cron, or a different tool.
Best for
CI and disposable environments where nothing persists anyway.
Mechanism 5: models.json apiKey with a command (!...)

Same idea as mechanism 3, but expressed in models.json. A leading ! marks the value as a command whose output becomes the key. 

# ~/.pi/agent/models.json
"apiKey": "!secret-tool lookup service my-llm user me"
Where the key rests
Only in the secret manager.
Timing and caching
docs "Commands in models.json run at request time and are not cached by Pi." So this runs per request, unlike mechanism 3's once-per-process behavior. That costs a process spawn per call and means a locked keyring fails each request individually.
Reload behavior
docs Opening /model reloads models.json, so edits (including key changes) take effect without restarting pi.
Best for
Quick wiring of a secret manager into a custom endpoint without touching auth.json. Mechanism 3 is usually the better home; see the ranking.
Mechanism 6: custom HTTP headers in models.json

Some gateways want the credential in a header other than the standard Authorization: Bearer. The headers map accepts literal values, $NAME interpolation, or !command, the same three forms as apiKey. Pi's docs mention this pattern for Cloudflare AI Gateway upstream auth. 

# ~/.pi/agent/models.json
"headers": {
  "X-Api-Key": "!secret-tool lookup service my-gateway user me"
}
Where the key rests
Wherever the chosen form puts it (literal: in models.json; interpolated: in the environment; command: in the secret manager).
Watch out
A literal header value is exactly as exposed as the excluded status-quo arrangement. Prefer the command form.
Best for
Endpoints whose auth header pi does not set by itself.
Mechanism 7: provider environment variables

For pi's built-in providers, export the documented variable before starting pi. Nothing is written to disk, which is why CI systems like it. 

export ANTHROPIC_API_KEY=sk-ant-...
pi

Mechanism 8: credential env object in auth.json

A stored API-key credential can carry an env map with supporting values (account IDs, gateway IDs, and similar). Those values take priority over the process environment for that provider only. Pi's docs show this for Cloudflare-style setups. 

# ~/.pi/agent/auth.json
{
  "cloudflare-workers-ai": {
    "type": "api_key",
    "key": "...",
    "env": { "CLOUDFLARE_ACCOUNT_ID": "account-id" }
  }
}
What it is for
Non-secret (or semi-secret) companion values, scoped to one provider, without polluting the global environment.
Best for
Multi-account setups and gateways that need extra identifiers alongside the key.
Mechanism 9: ambient cloud credentials (no key in pi at all)

Some platforms authenticate through their own SDK machinery. Pi reads whatever the platform's standard credential chain provides. You never hand pi a key.

  • Amazon Bedrock: named profile (AWS_PROFILE), IAM keys (AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY / optional AWS_SESSION_TOKEN), a Bedrock bearer token (AWS_BEARER_TOKEN_BEDROCK), ECS task credentials, or IRSA. Region via AWS_REGION / AWS_DEFAULT_REGION.
  • Google Vertex AI: GOOGLE_CLOUD_API_KEY, or Application Default Credentials with GOOGLE_CLOUD_PROJECT (alias GCLOUD_PROJECT) and GOOGLE_CLOUD_LOCATION, authenticated via gcloud auth application-default login, or a service-account key file via GOOGLE_APPLICATION_CREDENTIALS.
  • Azure OpenAI: AZURE_OPENAI_API_KEY plus either AZURE_OPENAI_BASE_URL or AZURE_OPENAI_RESOURCE_NAME.
  • Cloudflare AI Gateway: CLOUDFLARE_API_KEY, CLOUDFLARE_ACCOUNT_ID, CLOUDFLARE_GATEWAY_ID. The gateway can hold upstream credentials itself, or pass an Authorization header from models.json.
  • Cloudflare Workers AI: CLOUDFLARE_API_KEY plus CLOUDFLARE_ACCOUNT_ID (account ID can also live in the credential's env object).
Where the key rests
In the platform's own credential store (cloud config, keychain, token files), which is designed for rotation and short lifetimes.
Watch out
Many of these are still configured through environment variables, so the BOOM scenario applies to the identifiers. Short-lived tokens limit the damage.
Best for
When you already live in that cloud's identity system. Free rotation beats any hand-managed key.
Mechanism 10: runtime --api-key flag

Pass the key on the pi command line for a single run. It wins over everything else. 

pi --api-key sk-... --model provider/model
Precedence
✓ verified Observed as the winning source when all other sources were configured.
Exposure
platform Command lines are visible to the same user via ps and shell history. Treat this as printed.
Best for
One-shot experiments and CI jobs where the key is already in the job's secret store and the runner is disposable.
Mechanism 11: the SDK (ModelRuntime and friends)

When pi is embedded in your own program, you control credential storage entirely. Pi's SDK example (examples/sdk/09-api-keys-and-oauth.ts) shows three moves: 

import { createAgentSession, ModelRuntime, SessionManager }
  from "@earendil-works/pi-coding-agent";

// 1. Default locations (~/.pi/agent/auth.json, models.json)
const modelRuntime = await ModelRuntime.create();

// 2. Your own credential and model files
const customRuntime = await ModelRuntime.create({
  authPath: "/tmp/my-app/auth.json",
  modelsPath: "/tmp/my-app/models.json",
});

// 3. A key supplied at runtime, from wherever your app keeps secrets
await modelRuntime.setRuntimeApiKey("anthropic", "sk-my-temp-key");
Where the key rests
Wherever your application keeps it: vault, keyring, database. Pi never sees more than the resolved value in memory.
In-memory sessions
SessionManager.inMemory() keeps transcripts out of ~/.pi/agent/sessions entirely, which also shrinks the transcript-leak surface.
Best for
Products and services that embed pi. For an interactive terminal user this is overkill.
Mechanism 12: a provider extension with its own authentication

When a provider speaks a custom protocol or runs a custom auth flow, write (or install) a provider extension. The extension can register its own /login flow with display name, token refresh, and access-token resolution; pi then stores whatever the flow returns in auth.json. Native provider auth also supports custom credential resolution and provider-scoped environment.

Where the key rests
Whatever the extension's flow produces (usually auth.json), or entirely inside the extension's own logic.
Trust warning
docs "Provider extensions run inside Pi and can inspect credentials, prompts, tool definitions, model responses, and usage. Treat them as trusted code." Installing one is granting it your keys.
Best for
Providers pi does not support out of the box. Last resort, not first.
Mechanism 13: no key at all (local models and dummy keys)

Local endpoints need no real secret. Pi's docs show a dummy literal ("apiKey": "ollama") purely to satisfy the client; Ollama ignores it. The llama.cpp router integration needs nothing at all.

Where the key rests
Nowhere. The "key" is a public constant.
Best for
Local inference. Also the correct answer when an endpoint truly needs no auth.

Concrete recipe: the encrypted-store route, end to end

Mechanism 3 is abstract until you see it wired to real tooling. This machine already has an age-encrypted secrets store managed through mise (secrets:edit runs sops edit .env.local.json with the identity at ~/.config/mise/age.txt). The same store pi never touches can become pi's key source in three steps. Everything below was executed successfully on this machine ✓ verified, with values replaced by dummies or length-checked.

Step 1: keep the secret in the encrypted store

# Opens the sops-encrypted store in your editor (interactive).
# The repo's mise task pins the age identity for you.
mise run --raw secrets:edit

# Inside, keep a key like:
#   "MY_PROVIDER_API_KEY": "sk-..."
# The file is age-encrypted at rest and lives at .env.local.json (permissions 600).

Step 2: read one value back out (this is what pi will run)

SOPS_AGE_KEY_FILE="$HOME/.config/mise/age.txt" \
  sops --decrypt --extract '["MY_PROVIDER_API_KEY"]' /absolute/path/.env.local.json

Notes from probing: sops resolves through mise's tool installs, the extract prints just the value (I verified with | wc -c so no secret entered any log), and the sops CLI does need SOPS_AGE_KEY_FILE pointed at the identity explicitly.

Step 3: point pi at that command

# ~/.pi/agent/auth.json
{
  "my-provider": {
    "type": "api_key",
    "key": "!SOPS_AGE_KEY_FILE=\"$HOME/.config/mise/age.txt\" sops --decrypt --extract '[\"MY_PROVIDER_API_KEY\"]' /absolute/path/.env.local.json"
  }
}

Why this shape: the plaintext key exists in exactly two places: inside the age-encrypted store, and for a moment inside pi's memory when a request goes out. No environment variable, no world-readable config, and no ordinary agent command has a reason to print it. Rotation is "edit the store, restart pi" (recall that auth.json commands cache for the process lifetime).

Equivalents on other machines: macOS keychain as !security find-generic-password -ws 'my-provider'; Linux Secret Service as !secret-tool lookup service my-provider user me (present on this machine); any password manager CLI that prints a secret to stdout. The command only has to print the key and exit zero.

Decide by situation

🏠 Personal machine, one provider

Mechanism 3 with a keyring, or the sops recipe if you already keep secrets in an encrypted store. Fall back to mechanism 2 if you dislike the locked-keyring failure mode.

🔁 CI or a disposable runner

Mechanism 7 with a short-lived key, or mechanism 10 for a single step. The runner dies with the environment anyway; just make the key cheap to rotate and scope it down.

🧩 Custom OpenAI-compatible endpoint

Mechanism 2 or 3. Both give the endpoint a credential pi resolves internally. Keep models.json free of secrets so it stays safe to browse and share.

☁️ Deep in a cloud identity system

Mechanism 9. Platform-managed short-lived credentials beat any hand-copied key.

🧪 Embedded pi inside a product

Mechanism 11. Your vault, your rotation, in-memory sessions. Nothing pi-shaped stores anything.

🏠 Local models only

Mechanism 13. There is no key question to answer.

The ranking, with reasons

My full ordering for a personal machine: 3 (secret-manager command) > 2 (literal auth.json) > 1 (/login) > 8 > 9 > 5 > 6 > 11 > 4 > 7 > 10 > 12, with 13 outside the race.

  • 3 over 2: the secret stops existing in any file pi owns; casual reads find a command string, not a key.
  • 2 over 1: same storage, but mechanism 2 does not depend on a provider supporting a sign-in flow and is scriptable.
  • 1 over 8: a real credential flow gets you revocation and refresh; a stored literal gives neither.
  • 8 over 9: for providers without cloud identity, a scoped private file beats environment-carried identifiers.
  • 9 over 5: platform rotation and short lifetimes outweigh the elegance of a per-request command.
  • 5 over 6: fewer moving parts; a header map is for endpoints that demand it.
  • 6 over 11: for a terminal user, embedding pi is a bigger decision than where a key lives.
  • 11 over 4: in-process resolution beats the environment's accidental broadcast, when you can afford it.
  • 4 over 7: interpolation is at least scoped to the provider block.
  • 7 over 10: an environment variable does not show up in ps output for the whole session.
  • 10 over 12: a flag you control beats an opaque extension that can read everything.

Keeping keys out of transcripts

  • Never cat a file that may hold a secret. Inspect shapes with a masking script instead (see evidence section).
  • Remember pi auth print-api-key prints the real key on purpose. Use pi auth check --json (which returns only status) when you want to know whether credentials resolve ✓ verified.
  • Before sharing or exporting a session, search it for your key prefixes. Pi's security doc tells you to do exactly this.
  • When a key is ever printed anywhere, rotate it. Scrubbing copies is a maybe; rotation is a fix.
  • Prefer masked probes (wc -c, length checks, shape printing) whenever you verify secret plumbing.

Masked shape probe (safe way to inspect a credential file)

python3 -c "
import json
d = json.load(open('/home/YOUR_USER/.pi/agent/auth.json'))
def mask(o):
    if isinstance(o, dict): return {k: mask(v) for k, v in o.items()}
    if isinstance(o, list): return [mask(v) for v in o]
    if isinstance(o, str): return f'<str len={len(o)}>'
    return f'<{type(o).__name__}>'
print(json.dumps(mask(d), indent=1))"

Glossary

Agent directory
Where pi keeps user-level config. Default ~/.pi/agent, overridable with PI_CODING_AGENT_DIR.
auth.json
Pi's credential file. Holds API keys and OAuth tokens. Should be 600. Never commit it.
models.json
Where custom endpoints and model overrides live. Not a credential store; treat anything secret-shaped there as a liability.
Transcript
The session .jsonl file. It records tool calls and their output. Anything printed during a session lives there.
sops and age
sops encrypts values inside a structured file while leaving key names visible; age provides the public-key encryption underneath. One private identity file decrypts it.
Keyring
An OS service that stores secrets behind a login or unlock prompt, queryable by name (macOS Keychain, Linux Secret Service).
Interpolation
Replacing $NAME inside a config value with the environment variable's content when pi reads it.
