## Context

The maintainer decided 2026-07-20 that the rule-file format changes so a rule
can span lines and carry per-line comments, which the always-verbose
forbidden-regex engine was deliberately built to support
(`package/rust-module/forbidden-regex/src/parse/cursor.rs`, `skip_ignorable`
doc). The incumbent line-based format cannot express this. A block-form
extension was drafted (`doc/planning/forbidden-strings-block-rule-format.md`)
but the maintainer required a full design-space evaluation before
implementation; the maintainer then named NestedText as a candidate.

Measured incumbent facts:

- The scanner is not dependency-free: `package/cli/forbidden-strings/Cargo.toml`
  carries anyhow, clap, forbidden-regex, gix-hash, gix-index, ignore, memchr,
  rayon, tracing, tracing-subscriber; forbidden-regex pulls aho-corasick,
  memchr, regex-automata as prefilters. External crates parsing untrusted
  input (ignore, gix-index) are established inside the gate binary, so a
  parser crate is not hard-gated out; it is scored under human-auditability.
- Rule sources: `forbidden-strings.append.txt` (checked in),
  `forbidden-strings.append.local.txt` (gitignored, sensitive, hand-edited),
  `package/cli/forbidden-strings/data/builtin-rules.txt` (generated by the
  betterleaks porter, 259 rules, parsed again by `build.rs` for the embed).
- file-enforcer concatenates the append files into the runtime rules file;
  today concatenation is line-append. A format must either stay
  concatenation-safe or file-enforcer grows merge logic (scored, not hard).
- The repo TOML incumbent (`@monochromatic-dev/module-toml-edit`) is
  TypeScript-side only; no Rust TOML parser is incumbent.
- Redacted finding output (`PATH:LINE rule=N`) is format-independent and out
  of scope.

## Hard constraints

- Rules may span multiple lines and carry per-line comments
  (maintainer-ratified requirement).
- Both bare-literal and regex rule forms are expressible.
- Load errors are fail-closed and redacted.
- Parser source is inspectable and auditable at the commit-gate trust
  boundary (high-trust overlay; proprietary or uninspectable parsing is
  ineligible).
- The existing redacted finding output contract is unaffected.

## Base components and overlays

- External formats (NestedText, TOML, and discovered peers): inspectable
  open-source local technology (a spec plus either a parser crate or an
  in-house subset implementation; if a crate is adopted it is a second
  component and audited as such).
- Incumbent-lineage candidates (block form, distinct fences): custom format
  extension of the incumbent, eligible under the replacement overlay's
  keep-the-incumbent lineage.
- Overlays active for all candidates: incumbent replacement, high-trust
  execution, human-auditability.
- Not applicable: SaaS gates (no hosted component); native/Wasm/prebuilt
  overlay (no prebuilt artifacts; all code builds from source in-repo or from
  a source-auditable crate); sensitive-data residency overlay (rule files
  never leave the machine; the local appendix is already gitignored).

## Frozen criteria and weights

All weights 1 (no user-specified priorities; sensitivity will sweep 1
through 5). Ratings happen only after every finalist passes equal-depth
validation.

1. Authoring ergonomics for commented multi-line rules
   (the ratified core requirement, quality thereof).
2. Container-to-pattern boundary surface
   (escaping, collision, and misparse hazards between format and regex bytes).
3. Human-auditability of the parsing path
   (measured non-test source lines, control flow, dependency count of
   whatever parses the format at the gate).
4. Migration cost
   (three live files, build.rs embed, file-enforcer concatenation,
   binary-before-data-file release sequencing).
5. Ecosystem precedent and familiarity
   (peer secret scanners' rule formats; general format adoption).
6. Extensibility toward open rule-identity needs
   (named rules possible later without forcing that open decision now).
7. Spec and implementation maintenance health.

## Candidate ledger

### Incumbent-extended block form

- Discovery source: class 4 (drafted in
  `doc/planning/forbidden-strings-block-rule-format.md`).
- Base: incumbent-lineage custom extension. Overlays: replacement,
  high-trust, human-auditability.
- Screening: no hard-gate failure. In-house parser (inspectable), fail-closed
  design drafted, multi-line plus comments delivered. Collision audit of the
  three live files: zero colliding lines. Proceeds to targeted evidence.

### Distinct fence delimiters

- Discovery source: class 4 (design alternative in the same draft).
- Base: incumbent-lineage custom extension. Overlays: as block form.
- Screening: no hard-gate failure; same properties as block form with a
  second bespoke syntax. Proceeds (equal-depth rule) though preliminary
  soft outlook is weakest; soft outlook does not gate promotion.

### TOML

- Discovery source: class 3/4 (gitleaks precedent; betterleaks source config
  `betterleaks-default-config.toml` is TOML).
- Base: inspectable open-source technology (spec plus toml or toml_edit crate,
  or an in-house subset). Overlays: replacement, high-trust,
  human-auditability.
- Screening: no hard-gate failure. Multi-line via `'''` strings; comments
  cannot interleave inside a multi-line string (they become content), so
  per-branch comments must be engine-level first-column `#` inside the
  string or TOML comments outside it; escaping interactions exist in basic
  strings (literal `'''` strings are verbatim but cannot contain `'''`).
  Proceeds to targeted evidence.

### NestedText

- Discovery source: maintainer-named; primary spec fetched 2026-07-20
  (nestedtext.org, basic syntax page).
- Base: inspectable open-source technology (spec plus reference Python
  implementation; Rust implementations to be enumerated; in-house subset
  viable). Overlays: replacement, high-trust, human-auditability.
- Screening: no hard-gate failure. Spec properties on target for this use:
  multiline strings are `>`-prefixed verbatim lines with no escaping
  mechanism at all, and comment lines are ignored for adjacency, so comments
  legally interleave between the lines of one multiline string (spec:
  "Comment lines are ignored when determining whether adjacent lines belong
  to the same dictionary, list, or string"). Top-level list items
  concatenate by file append, matching file-enforcer. Proceeds to targeted
  evidence.

## Evidence records

### NestedText spec: verbatim multiline and interleaved comments

- Candidate: NestedText (spec, nestedtext.org, latest, accessed 2026-07-20).
- Claim: multiline strings are unescaped verbatim `>`-lines; comment lines
  may appear between them without breaking the string.
- Gate: screening (category fit for commented multi-line regex bodies).
- Status: pass.
- Source: nestedtext.org/en/latest/basic_syntax.html, sections on multi-line
  strings and comments.
- Outcome: NestedText structurally eliminates the container-to-pattern
  boundary (criterion 2) rather than managing it; per-branch comments are
  container-level.

### Incumbent gate binary already trusts external parsing crates

- Candidates: all (constraint interpretation).
- Claim: crate adoption is not hard-gated by repo practice; the gate binary
  already ships ignore, gix-hash, gix-index, clap parsing untrusted input.
- Gate: high-trust overlay interpretation.
- Status: pass (recorded inference; measured from
  `package/cli/forbidden-strings/Cargo.toml` dependency table).
- Outcome: crate-versus-in-house-subset is scored under criterion 3, not
  hard-gated.
