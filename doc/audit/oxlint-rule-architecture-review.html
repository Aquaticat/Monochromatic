Executive summary

What this audit found

Monochromatic uses Oxlint to enforce both ordinary correctness rules and project-specific coding laws. Those project laws are implemented by five JavaScript plugins that register 88 named rules across 287 production TypeScript files. Physical line counts total 57,185, including comments and documentation.

Most of that code is not architecturally shallow. The largest plugin, the semantic readonly analyzer, already hides complex behavior behind a small rule interface. File count alone is not evidence that a module should be collapsed.

The clearest shallow area is different: directive governance. Twenty files each supply only a protected rule identity, description, and diagnostic message to one shared implementation. Deleting those files would concentrate their knowledge in one module without changing any external rule name. That is the top recommendation.

Top recommendation

Collapse directive governance

Keep all existing Oxlint rule names, but author their shared behavior and policy data in one deep module.

Read the evidence and trade-offs

What choosing a candidate means

Choosing a candidate does not authorize an implementation yet. It starts a design conversation that tests constraints, preserves required behavior, decides what belongs behind the seam, and identifies which tests must survive. This report deliberately describes behavior and structure without proposing TypeScript interfaces.

System primer

What Oxlint does in this repository

Oxlint reads source files, builds syntax trees, runs enabled rules, and reports diagnostics. A diagnostic is a concrete complaint tied to source text, such as “switch statements are banned.” A rule is the module that decides when to report that complaint.

Rule

One enforceable law

Example: no-restricted-syntax/no-switch visits every switch statement and reports it.

Plugin

A published rule collection

A plugin gives Oxlint a name and a collection of named rules. Config can enable each rule separately.

Config

The selected policy

The shared config chooses plugin locations, enabled rule names, severities, ignored paths, and overrides.

A concrete example: banning a switch statement

Source that violates the rule

switch (status) {
  case 'ready':
    run();
}

A comment that would normally suppress it

// oxlint-disable-next-line no-restricted-syntax/no-switch -- legacy code
switch (status) {
  case 'ready':
    run();
}

This repository also enables no-disable-no-switch. That second rule scans comments and reports the suppression itself. In plain language: the project bans switch statements and also bans bypassing that ban with an inline disable comment. Candidate A concerns the family of rules that govern these comments.

Primary source: package/oxlint-plugin/no-restricted-syntax/src/rule/_ban-disable-factory.ts:58-111 implements the shared comment scan and report behavior.

How configuration reaches Oxlint

The root file oxlint.config.ts imports and spreads @monochromatic-dev/config-oxlint. That package has two paths to the same five plugins. The development path points directly at TypeScript source. The built path points at co-located JavaScript sidecars using file:// URLs. A sidecar is a separate built plugin file placed next to the built config file.

What “built artifact” means here

TypeScript source is what maintainers edit. A build turns that source into files under locations such as dist/final. Those emitted files are the artifact that users actually load. A test that imports source can pass even when the emitted artifact is missing an export, bundles the wrong code, or differs in another build-only way. This repository therefore makes tests import built output when a package has a build task.

This policy is central to Candidates C and D. It explains why internal test helpers are re-exported from built package entries instead of being imported directly from source.

Architecture vocabulary

How this report judges structure

These words have precise meanings. The report uses them consistently so a recommendation can be checked rather than accepted as a vague request to “clean up” code.

Module

Anything with an interface and an implementation. A module can be one function, one file, one package, or a larger slice. File count does not determine module count.

Interface

Everything a caller must know to use a module correctly: names, inputs, outputs, errors, ordering, configuration, and important performance facts.

Implementation

Behavior hidden inside the module. Deepening aims to move knowledge here so callers do not repeat it.

Deep and shallow

A deep module provides substantial behavior through a small interface. A shallow module exposes nearly as much knowledge as its implementation contains.

Seam

A place where behavior can change without editing the caller. The interface lives at the seam.

Adapter

A concrete implementation used at a seam. In this report, source-resolved plugin paths and built sidecar paths are two adapters for loading the same plugin identities.

Leverage

What callers gain when one small interface provides behavior to multiple call sites and tests.

Locality

Change, bugs, knowledge, and verification stay in one place instead of being repeated across callers.

Leakage

Knowledge that crosses a seam and must be repeated elsewhere. In this report, leakage is architectural, not a security incident.

The deletion test

Imagine deleting the suspected shallow module. If its complexity disappears, it was pass-through. If the same knowledge must be repeated across callers, it was earning its place. A good deepening candidate lets deletion concentrate knowledge instead of spreading it.

The interface is the test surface

Callers and tests should normally cross the same seam. Tests that require many implementation facts can force the interface to mirror the implementation and can break whenever internals move.

Two adapters make a real seam

One adapter can be unnecessary indirection. Two adapters prove that behavior genuinely varies at that seam. The source and built plugin-loading paths in Candidate B satisfy this test.

Method and confidence

What was measured and how badges were assigned

The audit read plugin entry points, rule implementations, focused tests, package documentation, shared config source, relevant planning records, installed Oxlint 1.75.0's configuration schema, and git history for the addition of the test-import plugin.

File and line counts were measured from the current working tree. Rule-family uniformity was checked structurally: every directive-governance file has one exported constant initialized directly by banDisableRule, one ruleId, and no function, class, or type declaration.

An independent reviewer challenged the candidate scopes. Its main corrections are incorporated here: Candidate B does not pretend static package dependencies or physical sidecar files can disappear; Candidates C and D are separated because their test observability differs.

Strong

The deletion test passes, required behavior is known, and evidence supports the proposed scope.

Worth exploring

The opportunity is real, but tests or constraints must prove which parts may move behind the seam.

Speculative

Friction exists, but the deletion test passes only for part of the scope or the replacement test surface is not yet proven.

in-process

The candidate is TypeScript computation or build configuration with no remote dependency.

local-substitutable

The candidate touches the local filesystem or Oxlint process, but disposable fixture directories provide a realistic test adapter.

Candidate A

Collapse directive governance

Replace twenty data-only authoring modules with one deep directive-governance module while keeping all external Oxlint rule names and diagnostics stable.

Strong in-process Rank 1

Background in plain language

The no-restricted-syntax plugin registers ordinary bans such as no-switch and a second family whose names begin with no-disable-. Each second-family rule protects one target rule from being suppressed by an inline oxlint-disable comment.

All twenty protected-rule files call the same factory. Their only unique information is three pieces of data: the target rule identity, a documentation description, and a diagnostic message. None contains custom detection behavior.

What changes in daily work

Today
  1. Create a new no-disable-*.ts file.
  2. Repeat the factory call and three data fields.
  3. Import the new constant in the plugin entry.
  4. Register the external rule name in the plugin entry.
  5. Decide whether to add another config entry.
  6. Keep the explicit test catalog synchronized.
After deepening
  1. Record the protected rule's policy data in one module.
  2. Derive the same external rule registration from that data.
  3. Record whether the rule is enabled or intentionally registered but off.
  4. Retain the explicit rename-guard test list as an independent contract.

Deletion test

Question: If the twenty individual files disappear, where does their complexity go?

Answer: Their unique knowledge is only policy data. It concentrates in one module. No caller needs to learn twenty different behaviors because there are not twenty different behaviors. This is a clean pass.

Benefits

  • Locality: protected-rule identity, message, and configured state live together.
  • Leverage: one implementation serves every protected rule name.
  • Drift visibility: registered-but-off rules become explicit policy decisions.
  • Test stability: existing tests can continue using external rule names.

Costs and constraints

  • The twenty external rule names must remain independently configurable.
  • The explicit BAN_DISABLE_RULES test list should remain independent.
  • Diagnostics and inline suppression matching must remain byte-for-byte compatible.
  • This candidate does not absorb unrelated syntax-rule families.

Open decision before implementation

no-disable-max-lines and no-disable-no-misused-promises are registered by the plugin but are not enabled in restriction.ts. The deepened module should record whether this is intentional. The existing planning document already names the same pair, so this is not a new discovery, but the source count has moved from the document's 19 directive rules to 20.

Sources: doc/planning/oxlint-plugin-decomposition.md:9-14,98, package/oxlint-plugin/no-restricted-syntax/src/index.ts:125-145, and package/config/oxlint/src/rule/restriction.ts:181-198.

Candidate B

Concentrate plugin deployment identity

Keep the real source and built adapters, but stop repeating the same plugin identities across three TypeScript lists.

Strong in-process Rank 2

Background in plain language

Each custom plugin has one identity, such as test-import. The config package currently repeats that identity in the development entry, the built entry, and the Rolldown build input. It also needs a physical sidecar entry file and a static package dependency.

Repetition is not automatically wrong. The source and built paths are genuinely different adapters. What repeats unnecessarily is the inventory of which plugins exist and how each identity maps to those adapters.

Why two adapters must remain

The installed Oxlint version is 1.75.0. Its configuration schema accepts a JavaScript plugin entry as either a path or package-name string, or an object containing name and specifier. It does not accept an in-memory plugin object. The built config must therefore point to actual sidecar files, while development can point to TypeScript source files.

Installed primary source: node_modules/oxlint/package.json:3 and node_modules/oxlint/configuration_schema.json:10851-10875.

Concrete evidence from the last plugin addition

Commit 675ee22e3 added the test-import plugin to shared config. One plugin identity required hand edits to six config-package files. The lockfile change was generated separately.

Only three of these express repeated deployment identity. Package dependency, physical sidecar entry, and rule severity remain separate responsibilities.

Exact scope

Knowledge that can concentrate
  • The inventory of plugin identities.
  • The source package specifier for each plugin.
  • The sidecar output name for each plugin.
  • The Rolldown input name derived from the same identity.
Responsibilities that must remain separate
  • package.json remains a static dependency declaration.
  • Each physical plugin-*.ts entry remains a build input.
  • Rule enablement and severity remain config policy.
  • Generated lockfile changes remain package-manager output.

Deletion test

Question: If a shared deployment-identity module is later deleted, what happens?

Answer: The same identity mapping must reappear in the development entry, built entry, and Rolldown config. The proposed module would therefore concentrate real knowledge used by three callers. The two loading adapters remain separate because they genuinely vary.

Benefits

  • Locality: plugin identity is recorded in one TypeScript module.
  • Leverage: three representations derive from one inventory.
  • Parity: tests can prove source, built, and build-input sets agree.
  • Future additions: fewer repeated hand edits can drift.

Costs and constraints

  • The registry must be inlined at build time, not become a runtime dependency.
  • Separate sidecars and plugin namespaces from issue 238 remain invariant.
  • Static package dependencies still require an explicit edit.
  • A physical entry file still exists for every sidecar.

Existing drift that demonstrates the friction

src/index.node.ts says the sidecars are emitted by tsdown.node.config.ts, but the current build file is rolldown.node.config.ts. This stale comment is not itself the architectural problem. It is concrete evidence that deployment knowledge is repeated and can diverge.

Sources: package/config/oxlint/src/index.node.ts:4-5,21-49 and package/config/oxlint/rolldown.node.config.ts:17-25.

Candidate C

Test test-import through its rule interface

Move observable helper behavior into end-to-end rule scenarios so the built package entry no longer needs to expose every classifier and path helper solely for tests.

Worth exploring local-substitutable Rank 3

Background in plain language

The test-import plugin's built entry has two audiences. Production config imports the default plugin. The package's own tests import named classifiers and path helpers from the same built entry. The source explicitly marks those named exports @internal and says they exist so tests can obey the package's own built-artifact rule.

This is an intentional design, not accidental leakage. The question is whether behavior that users observe through diagnostics should be tested through the rule interface instead of through each helper interface.

Primary source: package/oxlint-plugin/test-import/src/index.ts:3-8 documents why the named exports exist.

What rule-level scenarios can observe

Manifest and artifact behavior

A fixture package can declare a built entry, import source from a test, and assert that the rule reports the import. It can also prove that source-pointing entries do not count as artifacts.

Build-task behavior

A disposable package can omit a build task and prove that the rule remains silent, then add a build task and prove that enforcement activates.

Path normalization behavior

Imports containing traversal segments can prove that a path merely resembling dist/final is still rejected after normalization.

Fixture allowlist behavior

A test-support module can re-export source and prove that the rule catches this laundering path.

Deletion test

Question: If helper exports leave the built package entry, does their behavior vanish?

Answer: No. The behavior concentrates behind the rule and remains observable through diagnostics in disposable packages. The deletion test appears to pass for these helpers, but each focused test must first be mapped to an equivalent rule scenario.

Benefits

  • Locality: tests describe rule behavior, not helper arrangement.
  • Leverage: one scenario crosses parsing, package lookup, and classification.
  • Interface depth: the built entry stops mirroring helper structure.
  • Refactor survival: tests can survive internal file movement.

Costs and preconditions

  • Rule scenarios spawn local Oxlint processes and use more fixture setup.
  • Every helper test needs an explicit scenario replacement before deletion.
  • Failure messages may be less local than direct helper assertions.
  • The package's own built-artifact testing law must continue to hold.

Existing test seam: package/oxlint-plugin/test-import/src/oxlint-test-import.unit.test.ts:73 begins the current end-to-end suite; eight sibling test files import helper behavior from built output.

Candidate D

Narrow prefer-readonly test probes selectively

Replace only those internal built-entry probes whose behavior can be proven through the readonly rule's diagnostics. Keep probes for cache, authority, and performance facts that diagnostics cannot reveal.

Speculative local-substitutable Rank 4

Why this is separate from Candidate C

The prefer-readonly plugin is a semantic analyzer with caches, authority data, branded effect slots, a TypeScript bridge, and cross-file summaries. Some tests inspect observable diagnostics. Other tests inspect internal facts such as cache statistics or the exact number of verified standard-library readers. Those facts do not necessarily change a diagnostic.

Treating all 17 built-entry test files as replaceable would be inaccurate. Candidate D asks for a per-test observability audit, not a wholesale interface reduction.

Why removal needs a mutant gate

The package entry documents one precise history: a mutant that restored incorrect formal-to-actual argument indexing survived the whole suite. The package therefore exports formalArgumentIndexes for a direct built-artifact test. A mutant is an intentional code change used to check whether tests detect the wrong behavior.

That export may leave the interface only after a rule-level fixture reproduces the spread-argument case and demonstrably kills the same mutant. Similar traceability is required for every proposed deletion.

Primary source: package/oxlint-plugin/prefer-readonly-parameter-type/src/index.ts:111-123 records the escaped mutant and why the test export exists.

Deletion test

Observable diagnostic helpers: deletion can concentrate behavior behind the rule if a scenario proves the same outcome.

Cache, authority, and performance probes: deletion can remove test observability rather than concentrate complexity. Those probes fail the test unless another reliable surface exists. This mixed result is why Candidate D is speculative.

Potential benefits

  • Rule-level regressions cover orchestration rather than isolated helpers.
  • The published interface can stop growing for replaceable probes.
  • Tests for observable behavior survive internal file movement.

Costs and stop conditions

  • Keep any probe whose fact cannot be observed through diagnostics.
  • Keep any probe until its historical mutant is killed elsewhere.
  • Do not weaken cache, lifecycle, authority, or performance verification.
  • Do not import source from tests as an escape from the artifact policy.

Ideas examined but not recommended

Why obvious-looking refactors were excluded

A useful audit states what it rejected. Otherwise a reader cannot tell whether an omission was deliberate or merely overlooked.

Do not collapse the entire readonly analyzer

The prefer-readonly plugin has 137 production files, but those files collectively form one large implementation behind a rule interface and an effect-summary interface. Deleting focused effect files would move the same semantic complexity into larger files. It would not concentrate knowledge.

The implementation plan also explicitly chose focused sibling modules for the host rule, semantic adapter, readonly classifier, effect summaries, TSDoc effect lookup, and suggestions.

Source: doc/planning/replace-prefer-readonly-parameter-types.md:955-969.

Do not merge all plugin sidecars or namespaces

The built config uses separate sidecars because Oxlint registers a plugin namespace from each loaded plugin. Merging files would force rule-name migration or lose independent namespaces. Issue 238 measured a merged-sidecar prototype and found no clear runtime justification for that migration.

Candidate B preserves the separate sidecars. It concentrates only the repeated inventory that feeds them.

Sources: repository issue 238 and package/config/oxlint/src/index.node.ts:26-49.

Do not generalize Candidate A to every rule factory

The method-call factory has three consumers and may offer a smaller later cleanup. The simple-ban factory has seven consumers, but it permits rule-specific predicates. For example, no-nullish-union defines custom shouldReport behavior. These families are not as uniformly data-only as directive governance.

Candidate A stays narrow because all twenty files passed the same structural uniformity check.

Sources: package/oxlint-plugin/no-restricted-syntax/src/rule/_simple-ban-rule.ts:71-123 and package/oxlint-plugin/no-restricted-syntax/src/rule/no-nullish-union.ts:133-145.

Do not treat the current test exports as accidental

Candidates C and D revisit deliberate choices. The test-import entry explicitly says internal exports exist so tests can exercise built output. The readonly entry records focused probes added because broader scenarios missed defects or mutants.

Any narrowing must replace evidence before removing its current seam. “Fewer exports” is not a goal that outranks regression detection.

Comparison and ranking

Which candidate should go first

1

Collapse directive governance

Best deletion test, uniform source shape, stable external rule names, and existing tests can remain at the plugin interface. The only prerequisite is confirming the intended state of two registered-but-off rules.

2

Concentrate plugin deployment identity

Real seam with two adapters and commit-backed friction. It ranks after Candidate A because physical sidecar entries and static dependencies remain, and build behavior needs parity verification.

3

Test test-import through its rule interface

Its helpers produce outcomes visible through diagnostics, so deepening is plausible. It ranks after Candidate B because every focused test needs a more expensive disposable-package scenario before its export can leave the interface.

4

Narrow prefer-readonly test probes selectively

Some probes may move behind the rule interface, but cache and authority facts may have no equivalent diagnostic surface. It ranks last because deletion is conditional and past mutants prove the risk.

Adjacent ranking reasons

  • A over B: A collapses uniformly data-only modules without crossing build adapters.
  • B over C: B has a proven recurring edit pattern; C first needs per-test scenario replacement.
  • C over D: C's helper outcomes are visible through diagnostics; D includes facts diagnostics cannot expose.

Decision guide

What happens after you choose

  1. Clarify constraints. Identify behavior that must not change, deployment assumptions, performance requirements, and external rule names that remain invariant.
  2. Apply the deletion test in detail. Trace every caller and test to prove knowledge concentrates instead of moving elsewhere.
  3. Design the deepened module more than one way. Compare alternatives on interface size, depth, seam placement, leverage, locality, and test survival.
  4. Choose tests before implementation. State which tests remain, which are replaced, and what regression each one protects.
  5. Only then authorize code changes. This report is an architecture audit, not an implementation decision.

Which candidate would you like to explore?

Fast choice

Choose A Lowest uncertainty and strongest locality gain. Choose B Reduce recurring config deployment drift. Choose C Deepen the artifact-rule test surface. Choose D Audit readonly probes without promising removal.
